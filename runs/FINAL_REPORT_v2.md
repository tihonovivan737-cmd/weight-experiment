# Прямая правка весов Qwen3.5-0.8B под GSM8K: итоговый отчёт серии

Отчёт собран скриптом `scripts/build_final_report.py` по сохранённым артефактам; каждое число читается из файла результатов, ничего не переписывается вручную. Предыдущий файл `runs/FINAL_REPORT.md` описывал более ранний этап серии и оставлен без изменений.

## 1. Что проверялось

Модель: `models/qwen3.5-0.8b` (`Qwen3_5ForConditionalGeneration`, 488 тензоров, 873 438 784 параметра, один файл 1 746 942 600 байт, хеш `04b1c301231dd422…`). Правка — прямая запись в файл весов: вычисление в `float32`, округление до `bfloat16`, форма и смещения тензоров не меняются. Обучения, градиентов, `LoRA`, готового `fine-tuning` и переноса весов из других моделей не было.

Условия вычислений едины для всей серии: одна физическая видеокарта `NVIDIA GeForce RTX 3090` (второй индекс), `bfloat16`, `batch` 1, `max_new_tokens` 1024, жадная выборка, промпт с обязательной последней строкой `FINAL: <число>`, сохранение по каждой задаче. Суммарное время генерации по всем сохранённым сводкам — 41,2 часа.

Наборы: `dev` (100 задач, хеш индексов `e40a7e0c…`) и `search` (250 задач, `266f6398…`) — только отбор; официальный `test` (1319 задач, `1c72e9e3…`) — только оценка, для отбора веток не использовался; удержанный набор `holdout6` (400 задач `train`, `261affef…`, эталонные ответы в файл не записаны) — одна финальная проверка.

## 5. Насколько эффект связан с оформлением ответа

Разделение сделано по задачам, где строка `FINAL` есть у обеих сравниваемых моделей: там оформление уже не отличает модели, и остаётся только арифметика (`scripts/quality_only.py`, `scripts/test_format_split.py`).

* Отборочные наборы, качество на пересечении: `w8` против исходной модели 197 → 204 (65,7 % → 68,0 %, p = 0,4350); `w50` против исходной модели 199 → 203 (p = 0,6835); `w50` против `w8` 215 → 214 (p = 1,0).
* Официальный набор: `w8` против исходной модели 662 → 648 (−14, p = 0,3830); `w50` против исходной модели 663 → 641 (−22, p = 0,1567); `w50` против `w8` 715 → 700 (−15, p = 0,1992).
* Общий прирост на официальном наборе при этом +44 (680 → 724, p = 0,01543) и +29 (680 → 709, p = 0,10872): целиком объясняется долей оформленных ответов (86,5 % → 93,9 % и 94,3 %) и сокращением обрывов (115 → 76 и 66).
* Потолок «идеального оформления» (`scripts/extraction_ceiling.py`): исходная модель 241 из 350, `w8` 237, `w50` 235, `w83` 233, `w84` 232, `w85` 232, `w86` 227, `w87` 228 — правки не расширяли множество задач, где нужное число уже написано в тексте, а только помогали его выбрать.
* На удержанном наборе из 400 задач тот же разбор (`scripts/holdout_ceiling.py`): потолок 247 у исходной модели, 251 у `w50`, 253 у `w8` при верных 199, 211 и 218 — разрыв между «посчитал» и «оформил» у всех трёх примерно одинаковый.

**Вывод: улучшить именно арифметику правкой весов в этой серии не удалось.** Единственный воспроизводимый эффект — дисциплина вывода: последняя строка `FINAL`, сокращение обрывов и укорочение ответа примерно на 13 %. Он подтвердился на всех трёх независимых друг от друга материалах: отборочном (350 задач), официальном (1319) и удержанном (400).

## 8. Ошибки серии, зафиксированные в журнале

* `w82` оказался байтовым дублем `w75`: гипотеза о распределении дозы при нейтральной сумме этой сборкой не проверялась (§93.2). После этого введён обязательный контроль уникальности хеша до прогона (§93.3), который и поймал бы повторенье раньше;
* прогонщик `w82` сорвался на раскладке каталога: `modify_weights.py` сам создаёт подкаталог `model`, а путь сборки был задан с `/model` — файлы легли вложенно, `dev` не выполнил ни одной задачи (§92.1);
* обёртка «чёрного окна» не распознала ответ сервера из-за пробела после двоеточия и остановилась, ничего не удаляя и не убивая процесс (§91.1);
* проверка приращений стека сначала была сделана через целочисленное усечение, что обнулило значения между −1 и 1 и дало ложное «отличий нет»; проверка переделана побитово, ошибка разобрана в §102 журнала серии (в тексте §98.1 об этом записи не было — добавлено отдельным блоком);
* несколько блоков журнала отвергались проверщиком за латинские слова вне списка и за иероглиф в тексте публикации — оба класса ошибок исправлены до вставки.

## 10. Итоговый вердикт

1. **Что проверено.** Прямая правка весов Qwen3.5-0.8B без обучения: 90 заготовленных рецептов, 83 собранных набора веса, 82 измеренных прогона, 81 уникальный хеш (80 из них измерены). Затронуты 22 семейства тензоров (перепись §102.3): гейт линейного внимания, строки вывода, нормализации, свёртки, ветви `MLP` и внимания, задержки и пороги.
2. **Что выбрано.** По правилу §97.8 опубликован `w50_finalrow_rotation15_smallmargin` (3 условия из 4 кредит-гейта, 217/340/10 на отборе, 709/1319 на официальном наборе). Контрольная точка `w8_z_gate_mild_format` (216/332/18; 724/1319) остаётся второй составляющей сравнения и на удержанных данных выглядит лучше `w50` (218 против 211 из 400, `p` = 0,3489 — значимо ничего).
3. **Насколько эффект связан с оформлением.** Полностью. Прирост верных задач сопровождается ростом доли строк `FINAL` (86,5 % -> 93,9 % и 94,3 % на официальном наборе; 84,8 % -> 92,5 % и 94,0 % на удержанном) и сокращением обрывов, а на подмножестве задач, где `FINAL` есть у обеих моделей, прирост исчезает или становится отрицательным.
4. **Что подтвердилось на удержанных данных.** Только направление и величина форматного эффекта: +12 задач у `w50` и +19 у `w8` против исходной модели из 400 (`p` = 0,2513 и 0,0642). Улучшения арифметики не подтвердилось ни у одной из 82 измеренных правок; наилучший одиночный прирост качества за серию (+8 задач) соответствует шуму (`p` = 0,28).
5. **Что осталось за пределами метода.** Модель по-прежнему решает 50…55 % задач GSM8K, а «потолок оформления» (232…253 из 350 и 247…253 из 400) выше текущего результата на 20…40 задач: резерв лежит в рассуждении, а не в выводе ответа. Правкой весов без обучения этот резерв не вскрывается.

## 12. Как воспроизвести и как откатить

```bash
cd /home/mpiscil/weight-experiment
```
